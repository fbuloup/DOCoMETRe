Testing a Process

A process can be run on its own, without subject, session or trial. This is the best way to check a process while it is being developed: wiring of sensors, sample frequencies, real time charts, ending conditions, workload of the real time system... Data acquired during a test are kept in a process test folder, so that they can be inspected exactly like the data of a trial.

Running a test

  1. Connect the real time system and check that the DACQ configuration associated with the process can reach it (IP address for ADwin, serial port for Arduino).
  2. Save and compile the process (automatic when Options > Build automatically is checked), and fix compilation errors if any: the compiled process is the one loaded into the real time system.
  3. Select the process in the Experiments view.
  4. Switch to the Acquire perspective: the process is displayed as the item to run. It can also be chosen there with the Select item to run button.
  5. Press Run (F9). The real time charts defined in the Charts tab of the DACQ configuration are displayed.
  6. The test ends when the process terminates (Terminate process function, for example) or when it is stopped (Esc or F9).

Unlike a trial, a test is run only once: there is no validation dialog and no next trial.

Parameters

When the DACQ configuration declares parameters (ADwin only, see the Variables tab), a test has no parameters file to read their values from. A Parameters values dialog is displayed before the test starts: type the value of each parameter and press OK (Cancel cancels the test). These values are saved in the DACQ configuration and proposed again at the next test.

Results of a test

A test creates the following resources next to the process (in the same experiment or folder):

  • a folder named test.ProcessName, of type Process test, associated with the process. It contains one samples file per recorded channel or variable, named ChannelName.samples (no prefix nor suffix, unlike the data files of a trial);
  • a diary named ProcessName_diary.log (ProcessName_journal.log in French), which reports the events of the run (see Diaries).

Back in the Design perspective, open the samples files with a double click to display them in the data editor: the sample frequency of each signal is found in the DACQ configuration of the process. Open the diary to check that no data have been lost and to read the duration and timings of the run.

When a test is run again, the diary is replaced. If the test.ProcessName folder already exists, DOCoMETRe asks whether it can be deleted: answer Yes to run the test (previous results are lost), or No to cancel it (for example to rename or copy the folder first). A test folder can also be deleted with Delete in the context menu.

Tips

  • Look at the workload displayed in the status bar of the Acquire perspective: a workload close to 100% means that the period of the real time loop is too short for the process.
  • If the diary reports data losses, increase the buffer size (B.S.) of the corresponding channels in the DACQ configuration.
  • Deactivating blocks (context menu > Toggle activated state in the process editor) is a quick way to test variants of a process.
  • To check the timings of a run in detail, see Troubleshoots with DOCoMETRe (-traceTrialTimings option) and General consideration on micro-controllers.
